# ETF 资金流追踪双站

两个只看**份额（亿份）**的 ETF 动向看板。不看价格、不看涨跌，只看钱是流进还是流出——因为 ETF 份额的增减，是申赎行为的直接证据，比成交量干净得多。

## 一、口径说明（先看这段，否则容易误读）

**全站单位统一为「亿份」，是份额，不是金额。** 这一点和很多同类看板不一样，务必分清：

- **份额（亿份）** = 基金被申购/赎回的份数，反映资金进出方向，不受净值涨跌干扰
- **规模（亿元）** = 份额 × 净值，会因涨跌而波动，看不出真实申赎

原站 `etf-flow-d0j.pages.dev` 的债券表显示 16388「亿份」，其实是把接口返回的**规模(元)**当成了份额(份)，数量级差约 100 倍。本站直接取交易所份额接口，已纠正。

国家队站额外提供「市值·亿元」列——那是收盘价 × 份额算出的真实金额，仅供直观参照，不是份额换算。

其他几个容易搞混的点：

| 概念 | 本站怎么算 |
| --- | --- |
| 净申赎 | 当日份额 − 前一交易日份额。**不含**新发基金上市首日的份额跳增 |
| 5 日 / 20 日变动 | 5 / 20 个**交易日**的累计份额差，不是自然日 |
| 20 日分位 | 当前 20 日累计净流入，在 2024 年以来全部历史时点中的百分位。95% 表示比历史上 95% 的时点都更极端 |
| 份额折算 | 遇到拆分/合并（如 588200 在 2026-07-20 份额 ×3.09），**不做复权**，按原始数据展示。这会体现为一次大额「流入」，看到异常跳变请先查公告 |
| 退市/清盘 | 最后一条记录的份额通常已归 0，此后不再计入。图例里以 `†` 标记已无最新数据的标的 |

## 二、数据从哪来、什么时候更新

| 数据 | 来源 | 官方口径的更新时点 |
| --- | --- | --- |
| 沪市 ETF 份额 | 上交所 `query.sse.com.cn` 基金规模接口 | 「总规模每交易日 23:00 更新」 |
| 深市 ETF 份额 | 深交所 `www.szse.cn` 基金规模报表（日频） | 「T 日晚间仅供参考，以 T+1 日早间更新的规模为准」 |
| 股指期货席位 | 中金所持仓排名（IH / IF / IC / IM） | 16:30–17:00 |

**本站的采集时间：每个交易日两次——当晚 23:30 采当日初值，次日早 08:45 采终值覆盖。**

为什么分两次：沪市 23:00、深市 23:20 才发布当日数据，23:30 跑能当晚就把 T 日放上页面；但深市官方口径是「T 日晚间仅供参考，以 T+1 日早间更新的规模为准」，所以次日早间再重抓一次 T 日，把初值覆盖成终值。

两场的**采集范围不同**，不只是目标日不同：

- 晚间 23:30：从「库内最新日 +1」往后推进，目的是把当日新数据写进来；
- 次日 08:45：从「库内最新日」**原样重抓**，目的是把 T 日初值覆盖成终值。沪市若也一律从「最新日 +1」推进，库内已到 T 时循环会直接越过目标日、一行都不采，早间这场就等于白跑。

全链路**幂等**：同一日期重复采、重复跑，结果完全一样，不需要交易日历，也不需要卡准点。休市日接口返回 0 条，程序自动认为非交易日，不报错。

**数据缺口怎么处理**：任一环节采集失败，本次运行**不发布页面**，线上保留上一版。所以看到页面日期没变，大概率是当天采集失败，等下一次运行自动续采（游标只进不退，但失败会让游标停住，不会跳过）。

失败分两级，不是一律停更：

| 情况 | 退出码 | 结果 |
| --- | --- | --- |
| 份额没采到 / 页面重建报错 | 1 | 不发布，线上保留上一版 |
| 只有 K 线或期货未就绪 | 2 | 行业站照常更新发布，国家队站保留上一版 |
| 全部成功 | 0 | 两站都发布 |

这样分的理由很实际：行业站只吃份额，国家队站还要收盘价（算净申赎与市值）和期货席位。东财 K 线偶发限流时，没必要让完全健康的行业站跟着停更。

**东财 K 线被限流怎么办**：表现为连续 `RemoteDisconnected`。程序按异常类型判断——连接被直接掐断时只重试 2 次就放弃（否则 18 只 × 5 次重试要烧十几分钟，还会延长封禁），且**连续 3 只失败即熔断**本轮，剩余留待下次运行自动补。GitHub runner 的境外 IP 实测未被限流（单只 1.3 秒），本机 IP 反而更容易被封；本机调试时加 `--skip-kline` 跳过即可。

## 三、目录结构

```
├─ scripts/
│  ├─ build_db.py        # 建库 + 各交易所接口封装（首次全量建库用）
│  ├─ collect.py         # 每日增量：份额 + K线 + 期货，含各类守卫
│  ├─ build_industry.py  # 生成细分行业站
│  ├─ build_gjd.py       # 生成国家队宽基站
│  ├─ check_page.py      # 库→网页逐格自检（92 子类 × 2415 日）
│  ├─ reconcile_origin.py# 与原站逐类对账（维护用，不参与日常流程）
│  ├─ fetch_cats.py      # 抓取原站分类分片
│  └─ run_daily.bat      # 本机定时入口（云端不通时的备用）
├─ 网页/
│  ├─ index.html         # 两站入口页
│  ├─ echarts.min.js     # 图表库（自托管，不依赖 CDN）
│  ├─ 国家队站/          # 生成产物
│  └─ 行业站/            # 生成产物
├─ .github/workflows/daily.yml   # 云端定时任务
└─ 部署说明.md           # 上线操作手册
```

**数据库不进仓库**（144MB，且每天变化），压缩成 47MB 放在 [Release `data`](https://github.com/BRFG/etf-tracker/releases/tag/data) 里，每次运行下载→增量→覆盖回写，仓库不会膨胀。

## 四、在本地跑

需要 Python 3.11+、`requests`、`openpyxl`。

```bash
pip install requests openpyxl

# 首次：全量建库（约 40 分钟，只做一次）
python scripts/build_db.py

# 日常：增量采集 + 重建两站
python scripts/collect.py

# 只采集不重建
python scripts/collect.py --no-build

# 自检：库里的数 vs 页面里的数
python scripts/check_page.py
```

`collect.py` 的退出码：`0` = 全部成功，`1` = 有失败项（失败明细同时写进 `数据库/collect.log`）。

**本机定时**（云端不通时备用）：任务计划程序里建每日 08:45，程序 `cmd.exe`，参数 `/c "...\scripts\run_daily.bat"`，起始于项目根目录。

## 六、已知限制

- **不能判断「谁在买」**：份额增加只说明有净申购，可能是国家队、险资、散户或做市商。只能结合期货席位和行情侧推。
- **份额折算会造成假信号**：拆分/合并当日会出现数倍跳变，程序不做复权，看到单日 ±30% 以上先查公告。
- **跨境/商品 ETF 的份额含义不同**：黄金、原油等品种受申赎机制影响，份额与资金流的对应关系弱一些。
- **非投资建议**：数据来自交易所公开接口，准确性以交易所为准。本看板只呈现事实，不构成任何买卖建议。

## 七、出问题了

| 现象 | 处理 |
| --- | --- |
| 页面日期停在某天 | 看 [Actions](https://github.com/BRFG/etf-tracker/actions) 最近一次运行，红叉就是采集失败，等下次自动续采 |
| 页面 404 | Pages 部署有 1–2 分钟延迟；另外确认 Settings → Pages → Source 仍是 GitHub Actions |
| 定时不再触发 | GitHub 规定仓库连续 60 天无提交会停用定时任务。每天有数据回写，一般不会触发；若真停了，手动 Run 一次即可恢复 |
| 想改标的/改分类 | 改 `scripts/` 下对应脚本后 push，下一次运行自动生效 |

维护记录与已知问题清单见 `审查问题日志.md`。
